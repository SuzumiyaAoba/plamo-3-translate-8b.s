# 実行用重みファイルの事前作成

GPU用の重みを、一度だけ別ファイルへ保存できます。8Bで通常行う「元BF16の読み込み→指数の解析→無損失圧縮」を、次回から「保存済みの圧縮ブロックの読み込み」に置き換えます。部分保持の場合は生成中の再読み込みにも使います。元のBF16全16ビットを保ち、演算は従来と同じFP32です。

## 作成と利用

```sh
# Nixパッケージ。取得済みの8Bから作成
./result/bin/plamo-prepare-weights --model 8b
# または nix run .#prepare-weights -- --model 8b

# リポジトリ内のモデルを使う場合
python3 tools/prepare_weights.py --model 8b
```

既定の保存先はモデルのディレクトリ内の`metal-cache-v1.bin`です。CLI・常駐APIのMetalバックエンドが、次回の起動時から自動で検出します。実際の保存形式が一致するブロックだけを使い、従来のメモリ予算内で保持します。8Bの計算用行列16,181,624,832バイトに対して、作成したファイルは12,295,487,488バイトでした。今回の初回変換は約36秒で、公式重みのSHA-256検証と全BF16値の復元照合を含みます。

元のsafetensorsはEmbedding・小さな重み・キャッシュ未収録部分の読み込みにも使うため残します。変換ファイルは追加のディスク容量を使います。変換は一時ファイルへ行い、完了時に置き換えます。既に起動中のワーカーは、開いている古いファイルを引き続き使えます。

保存先や利用の切り替えは次の通りです。

```sh
python3 tools/prepare_weights.py --model 8b --output /path/to/8b-cache.bin
PLAMO_METAL_CACHE=/path/to/8b-cache.bin python3 tools/server.py --model 8b --backend metal
# 同じバイナリで元の読み込み経路へ戻す
PLAMO_METAL_CACHE=off python3 tools/server.py --model 8b --backend metal
```

`PLAMO_WEIGHT_STORAGE=auto|raw|lossless`による保存形式の選択は従来通りです。通常BF16を選ぶ環境では、無損失圧縮のファイルは使いません。2Bなどの比較用に`prepare_weights.py --storage raw`も使えますが、今回の2Bでは起動短縮を確認できず、通常形式のモデルに対する事前変換は推奨していません。CPU・`--memory stream`は元の経路を使います。

無効なファイル、異なるリビジョン、形状・形式の合わないブロックは元の読み込みへ戻ります。理由は`compute.note`、実際の利用は次の累積値で確認できます。

| 診断値 | 意味 |
| --- | --- |
| `compute.disk_cache_hits` | 保存済みブロックをGPUで利用した回数 |
| `compute.disk_cache_weight_bytes` | その元BF16換算の合計バイト数 |
| `compute.disk_cache_storage_bytes` | コピーまたは直接参照した保存領域の合計量。ページ境界の余白を含む |
| `compute.disk_cache_mapped_bytes` | 上記のうち、一時Metalビューでファイルを直接参照した量 |

これらは現在の保持量や物理ディスクの読み出し量ではありません。同じ範囲の再利用も加算します。専用バッファの現在の保持量は従来の`memory.cached_weight_bytes`・`cached_storage_bytes`です。明示的なファイル読み込みは従来の`weight_io`にも含め、ファイルの直接参照は生成中の`weight_io.decode_mapped_bytes`にも記録します。

## 形式と検証

先頭に形式バージョン・元モデルのリビジョン・元ファイルのサイズ・ブロック一覧を保存します。計算用の行列は推論順に並べ、最大64 MiB相当の元BF16を単位として、各保存領域を16 KiB境界へそろえます。圧縮ブロックは既存の512値単位の形式そのもので、GPUカーネルは変更していません。

作成前に公式の固定SHA-256と元ファイルを照合し、圧縮時は各ブロックをGPUで復元して全BF16値をビット単位で比較します。起動時はファイル全体のハッシュを再計算せず、リビジョン・元ファイルサイズ・範囲・圧縮ヘッダーの全オフセットを検証します。保持する重みは既存のMetal共有バッファへ一括読み込みします。起動時の保持バッファまでmmapへ置き換える案は、2Bの起動が遅くなったため採用していません。

保持できない重みは、1トークンの射影に限り、事前変換した圧縮ブロックの読み取り専用mmapへ一時Metalビューを作り、GPUから直接参照します。元のBF16はGPUで全16ビットを復元します。1ビューは既存の読み込み領域以下（最大64 MiB）で、GPU完了後に破棄します。元ファイルのmmapはバックエンドを閉じるまで維持し、ファイルの原子的な置き換え・削除後も既存ワーカーの参照は有効です。専用の重みコピーやGPUの保持予算は増やしません。

OSは参照したファイルページを再利用・回収できます。これらのページは専用バッファの保持予算の外にあり、OS全体の使用メモリが同じになることや、全ページの常駐を保証するものではありません。`decode_staged_bytes`が0でも、ページインによる物理ディスクI/Oは発生し得ます。直接参照できない場合は圧縮済みデータのコピーへ戻り、対応する保存領域がなければ元BF16を読みます。複数トークンの入力処理は、圧縮展開で遅くなる条件があったため従来の元BF16経路を使います。保存済み領域の一括読み込みは最大64 MiBです。

```sh
make test test-tools
MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1 ./build/test-metal --require-gpu
python3 tools/verify_disk_cache.py --model 2b --storage raw --file /path/to/2b-cache.bin
python3 tools/benchmark_weight_cache.py --model 8b --storage lossless --file /path/to/8b-cache.bin --budget-mib 8192 --repeats 3
```

## 測定

Apple M2・24 GiB・macOS 26.5.1で、同じワーカーのファイル利用を無効・有効にし、実行順を交互にして3回比較しました。ウォームアップ要求を送らず、ready後に同じ要求を2回送ります。前後で保持量・保存形式が一致する組だけから中央値を算出します。8Bは比較専用ワーカーの重み保持とステージングの上限を8 GiBにそろえた部分保持条件で、2Bは全計算用重みを保持しています。OSのファイルキャッシュ・他アプリの状態は制御していません。

| 条件 | 元の読み込み | 事前作成ファイル |
| --- | ---: | ---: |
| 8B・起動 | 6.011秒 | 3.608秒 |
| 8B・ready後の初回トークン | 2.828秒 | 1.794秒 |
| 8B・2回目の初回トークン | 1.676秒 | 1.735秒 |
| 2B・起動 | 1.403秒 | 2.265秒 |
| 2B・ready後の初回トークン | 0.101秒 | 0.099秒 |
| 2B・2回目の初回トークン | 0.096秒 | 0.098秒 |

8Bの起動は約40%短縮しました。2回目の応答は改善しておらず、2Bの通常BF16では起動が遅くなりました。8B・2Bの各10要求で全状態・logitsのハッシュ、トークン列、テキストが一致しました（8Bは最大2生成トークン、2Bは最大12）。

各回、保持量、初回・2回目の応答、検証結果、ソースとバイナリのハッシュは[測定データ](benchmarks/weight-cache.json)に記録します。ファイル形式の変更だけで、保持済み行列の演算速度が上がるものではありません。起動とready後の応答は別々に判断してください。

上の表は起動短縮を導入した時点の結果です。生成中の再読み込みの変更は、[生成速度の測定データ](benchmarks/generation.json)で別に比較します。変更前の実行ファイルを保存し、次のように同じメモリ予算・保存形式で測定できます。

Apple M2・24 GiBで、8Bの重み保持とステージングの比較専用上限を6 GiBにそろえ、変更前コミット`758b1ab`のワーカーと交互に3組測定しました。GPUの専用保持領域は前後とも6,374,195,200バイト、読み込み領域は64 MiBです。81入力トークン・最大12生成トークンの要求で、中央値は次の通りでした。

| 生成中の計測 | 変更前 | ファイルをGPUから直接参照 |
| --- | ---: | ---: |
| 生成速度 | 0.521 tokens/s | 1.755 tokens/s |
| 1生成ステップ | 1.921秒 | 0.570秒 |
| 明示的な`pread`の量／ステップ | 7.79 GB | 0 GB |
| mmapの直接参照範囲／ステップ | 0 GB | 5.92 GB |

この条件の生成速度は約3.37倍です。明示的な読み込みはGPUからのページ参照へ移るため、物理ディスクI/Oが0になるという意味ではありません。OSのファイルページは専用保持領域の予算の外にあります。全6測定のトークン列・テキスト・全状態とlogitsのハッシュが一致しました。入力処理と起動時間はこの速度に含みません。

```sh
python3 tools/benchmark_generation.py --model 8b --baseline-worker /path/to/previous-worker --repeats 3
# 部分保持を再現する場合は、変更前のワーカーにも同じ比較専用上限を設定する
python3 tools/benchmark_generation.py --model 8b --baseline-worker /path/to/previous-6g-worker --budget-mib 6144 --repeats 3
```

起動・入力処理を除いた生成速度を測り、ウォームアップ後の要求でトークン列・テキスト・全状態とlogitsのハッシュを照合します。前後のGPU重み保持量が起動時・ウォームアップ後・測定後に一致する組だけを集計します。OSのファイルキャッシュと他アプリの状態は制御しません。
