# 推論の最適化と検証

CPUのFP32中間演算結果を保った最適化と、Metal GPUへの行列演算移行の記録です。現在のCLI・常駐APIはCの共通エンジンからCPUアセンブリとGPU Metalを選べます。従来の手書き AArch64 / NEON と Darwin syscall のCLIは`plamo-asm`です。以下の過去のCLI測定は、このアセンブリ経路を指します。いずれも元BF16の重みファイルを使います。

現在は起動時の先読み・GPUページ準備に加え、BF16の無損失キャッシュ、全層を一つのコマンドにまとめるGPU生成、FP32正規化の並列集計を実装しています。生成中の同期は、全行列を保持した2Bで73回、8Bで97回から、いずれも1トークンにつき1回になりました。[実装と検証手順](METAL.md)を参照してください。以前のMLP融合による測定は[FP32統一・同期削減の実測](METAL.md#fp32統一同期削減の実測)に残しています。

## GPU行列演算と共有メモリ

Metalバックエンドは元BF16を共有バッファへ直接読み込み、要求・生成ステップの間で再利用します。必要な場合は全16ビットを保存したまま圧縮して保持し、GPUで復元します。生成のAttention・KV・RoPE・正規化もGPUで処理でき、KVはCPUと同じ匿名メモリを共有します。入力処理のAttentionと、重みが収まらない場合の生成は既存の経路を使います。GPUの全演算はFP32で、加算順序によるCPUとの差を全logits・状態と生成トークンで検証します。[方式・起動・精度・検証手順](METAL.md)を参照してください。

## LM Studioとの速度差とCPU並列化

2026-11-09に同じ24 GiBのApple Silicon Macで調査しました。LM Studio側には8Bの`Q4_K_M` GGUF（約5 GB）があり、実行ログは6スレッドでした。この実装は公式BF16（約17.06 GB）を使い、変更前はCPU 1スレッドです。さらに単発CLI・`stream`では、大きな射影だけで約16.18 GBを毎ステップ読み直します。量子化形式、スレッド数、重みの保持量が異なり、両アプリの速度差をアセンブリカーネルだけの差とは扱えません。

LM Studioには[GPU offloadの自動設定](https://lmstudio.ai/docs/cli/local-models/load)もあります。今回のローカルログからGPUの実使用は確定できていないため、GPUが何倍の差を生んだかは測っていません。

最初の高速化では、GPU・量子化バックエンドの追加と、BF16・既存の演算結果を保ったCPU並列化の2案を比較し、後者を採用しました。以下はそのCPU最適化の記録です。後続のGPU実装は前節のリンク先に分けています。

- APIの大きな行列を出力行で分割し、永続pthreadワーカーと呼び出し元で計算します。既定は性能コア数、`--threads 1`で逐次実行できます。各行のFMAと最終加算の順序は変えません。
- 入力処理では約1 MiBの行ブロックを全入力トークンで使ってから次の行へ進みます。同じBF16重みをCPUキャッシュ内で再利用します。この変更は単発CLIにも適用します。
- 重みの取得と計算を分け、計算専用のアセンブリ入口は取得・キャッシュ調整・再スケジュールをしません。全スレッドの終了まで借りた領域を維持します。
- I/Oの行境界はprefillとdecodeで一致させ、入力処理で保持した重みを生成時にも使えます。CPUキャッシュ用の小さな行ブロックとは別に扱います。

2Bの`resident`、`Hello.`の21入力トークン、生成1ステップを同じ条件で比較しました。保存した変更前ワーカーと変更後ワーカーを順に実行し、初期読み込み・キャンセル検証を除く3要求の中央値です。

| 項目 | 変更前・1スレッド | 行ブロック化・1スレッド | 行ブロック化・4スレッド |
| --- | ---: | ---: | ---: |
| 入力処理 | 1.524秒 | 1.278秒 | 0.419秒 |
| 生成1ステップ | 0.236秒 | 0.237秒 | 0.105秒 |
| 要求全体 | 1.758秒 | 1.516秒 | 0.525秒 |

要求全体は約3.35倍、入力処理は約3.63倍、生成は約2.24倍です。3条件とも元の重みの全常駐で、推論中の明示的な重み読み込みは0です。トークンID・出力テキスト・入力処理後と生成後のlogits/状態のハッシュが全要求で一致しました。異なる量子化形式のLM Studioと同等になったという測定ではありません。

8Bの`stream`も同じ入力・3要求の中央値で比較しました。こちらは両条件ともprefill＋decodeで32,363,249,664バイトを明示的に読み込みます。

| 項目 | 変更前・1スレッド | 変更後・4スレッド |
| --- | ---: | ---: |
| 入力処理 | 9.551秒 | 6.243秒 |
| 生成1ステップ | 5.458秒 | 5.182秒 |
| 要求全体 | 15.016秒 | 11.413秒 |

8Bの都度読み込みでは要求全体が約1.32倍にとどまります。生成はI/Oが支配的で、計算の並列化だけでは改善が小さいためです。既定の`auto`は保持できた範囲のI/Oを省きますが、速度は空き・保持量・OSの圧縮とページングに依存します。単発CLIにも行ブロック化を適用し、同じ8Bプローブの入力処理は9.393秒→8.691秒でした（各2回）。CLIは引き続き1スレッドです。

別の文章（51入力トークン、生成上限8トークン）でも2Bの変更前後でトークンID・logits/状態のハッシュが一致しました。要求全体は5.244秒→1.754秒です（2回の中央値、途中までの生成）。0.8Bの自動スレッド選択・連続要求・キャンセル後の再要求も実モデルで確認し、31Bはビルドとモデル不要のローダーテストまでを確認しました。

元データ・測定条件・ハッシュ・I/O量は[CPU並列化の測定結果](benchmarks/cpu-parallel.json)に保存しています。2/4スレッドの合成演算テストとHTTPを含む42件のPythonテストも通過しています。追加のThreadSanitizer検査は、ローカルmacOSのsanitizer初期化中に`main`到達前に終了し、完了していません。

保存したワーカーとの比較例:

```sh
# 変更前に保存（モデルごとに対応するワーカーを使う）
cp build/2b/plamo-worker /tmp/plamo-worker-2b-before
# 変更・再ビルド後
python3 tools/verify_api.py --model 2b --translate --memory resident --worker /tmp/plamo-worker-2b-before --repeats 3 --report build/before.json
python3 tools/verify_api.py --model 2b --backend cpu --translate --memory resident --threads 4 --repeats 3 --report build/after.json
```

`--text`と`--max-tokens`で別の入力・生成上限も測れます。上限で止まった結果は文章全体の翻訳速度とは区別します。`auto`では保持量とOSの圧縮・ページングが速度に影響するため、同条件の比較には`resident`または`stream`を明示してください。

## 前回の最適化結果（単発CLI）

Apple Silicon、macOS 26.5.1、24 GiB RAM。英日翻訳 `Hello.` の公式プロンプト21トークンを入力し、最初の出力51871（「こんにちは。」）と、続く終了16を計算しています。入力処理と1回の cached decode をエンジンの内部で分けて測定しています。最適化前は4行同時の行列ベクトル積・層単位の逐次 prefill・mmap からの重みロードです。最適化後は2回の中央値です。

| 項目 | 最適化前 | 最適化後 | 改善 |
| --- | ---: | ---: | ---: |
| 入力処理（21トークン） | 50.28秒 | 9.09秒 | 5.53倍 |
| 生成1ステップ | 34.79秒 | 5.22秒 | 6.67倍 |
| 上記の合計 | 85.08秒 | 14.31秒 | 5.95倍 |

初期化はどちらも約0.05秒で、この合計には含めていません。トークナイザー・テキスト表示も上のエンジン計測には含めていません。CLI でも英日「こんにちは。」・日英「Hello.」の出力と正常終了を確認しています。タイミングは OS キャッシュ・メモリ圧・CPU の実行状態で変わります。

別に測ったトークン化コマンド（語彙構築・起動を含む5回の中央値）は、0.796秒から0.0326秒へ短縮しました。初回起動はコード検証などにより遅くなることがあります。

## 採用した変更

### 重みを最大1 GiBの一時領域へまとめて読む

最大の問題は計算だけではなく、16 KiB程度のページごとに発生する重み読み込みの費用でした。最適化前は約100万回のページフォルトが各 forward で観測されました。

safetensors ヘッダーの mmap と名前・形状の照合は維持し、大きな行列だけを `pread` で元の BF16 バイトのまま匿名領域へ読み込みます。1回8 MiBまでの読み込みとし、最大1 GiBの同じ領域を使い回します。重みの FP32 コピーやファイル変換は作りません。小さな正規化重み・埋め込み行は従来のマッピングを使います。

読み込み失敗・非モデル領域などでは元のマッピングへ戻れます。モデル初期化に失敗した場合のマッピング・FDの解放と、再試行もテストしています。一時領域は次の行列演算まで有効で、推論エンジンは1スレッドです。

比較した方式:

| 方式 | 入力処理 | 生成1ステップ | 判断 |
| --- | ---: | ---: | --- |
| 4トークン化など、mmap 読み込みのまま | 38.65秒 | 33.46秒 | 演算だけでは不十分 |
| 行列ごとに `MADV_WILLNEED` | 14.62秒 | 10.12秒 | フォールバックとして残す |
| 元バイトのまとめ読み | 10.18秒 | 5.71秒 | 採用、後続の演算改善でさらに短縮 |
| まとめ読み＋次の層の先読み | 15.49秒 | 11.92秒 | RSSも約9.7 GBへ増えたため不採用 |

これらは検討途中の別々の測定で、最終版の中央値とは異なります。不採用の次層先読みコードは製品から除去しています。

### 入力トークン間で行列のロードと変換を共有

各層で正規化・QKV射影・Attention・出力射影・MLPを段階に分け、独立した大きな射影をまとめて計算します。Attention とキャッシュ追加は引き続き因果順に処理します。

4トークン×4行、8トークン×2行、8トークン×3行を測り、現在は8×3を主に使います。行の端数には8×2や汎用経路、入力数が少ないときには4×4や行列ベクトル積を使います。各出力の4レーンの FMA 順序と最後の加算順序を維持します。入力が2〜3トークンでも、大きな射影ごとに一度だけ重みを取得します。

作業領域は prefill 中に一度確保し、全層で再利用して解放します。解放後の次トークン生成もテストしています。

### 生成用の8行同時計算

行列ベクトル積は8行を同時に処理し、内側ループを16列分に展開しました。128 MiB の行列で、以前の4行カーネル約6.1 msに対し約4.6 msです。行・列の端数には元の経路を残しています。

### Attention・活性化・キャッシュの SIMD 化

- 4つのキーを転置して並行計算し、各スコアの加算順序を維持する。
- 値の加重和は4成分を並行計算し、各成分のトークン順を維持する。
- 指数関数の多項式、SwiGLU、softmax の指数・除算、RMSNorm の適用、残差加算を SIMD 化する。
- RMSNorm の分散と softmax の和は、従来の逐次加算順を維持する。
- キャッシュのスライディングコピーを SIMD 化し、コピーと RoPE を一つの読み書きにまとめる。

### RoPE の過去キーを再利用

回転前キーを残し、各層の回転済みキーを保持します。キーが1つ増え、倍率が同じ場合は新しいキーだけを処理します。リセット・倍率変更・スライディングで座標が変わる場合は元のキーから再計算します。このため再回転による誤差を蓄積しません。

最大コンテキストでは回転済みキーの保持に追加メモリを使います。表の約0.90 GBは短い入力での常駐量で、長文時の上限ではありません。

### 語彙先頭文字の直接索引

Trie の先頭文字を Unicode 符号位置で直接引ける、任意の索引を追加しました。連結リストを走査する従来経路も残っています。語彙・スコア・分割規則・トークン ID は変更しません。

## 一致の検証

- 行列カーネルの符号付き入力、任意のストライド、空形状、端数でビット一致。
- 2層モデルの40ケースで全状態・logits・KVキャッシュを比較。既存prefix、スライディング、prefill後の生成を含む。
- 活性化71形状、Attention49形状、RoPE の端数、キャッシュコピーの重なりを旧実装と比較。
- 語彙107,520件、公式トークナイザーとの33ケース、Unigram区間の独立参照210ケースを検証。
- 実8Bモデルの prefill と cached decode の全logits・最終状態、合計892,928バイトを最適化前と直接比較して一致。
- 英日・日英 CLI、全323テンソルの形状登録、`nm -u build/plamo` が空であることを確認。

完全一致はこのアセンブリ実装の最適化前との比較です。PyTorchが別の加算順序で実行する任意の入力とのビット一致を意味しません。

## 再実行

```sh
make all test
make build/bench-matvec build/bench-matmul
./build/bench-matvec
./build/bench-matmul
python3 tools/benchmark.py --repeats 3
```

`tools/benchmark.py` は実重みを使い、固定の翻訳プローブの token ID・logits・最終状態のハッシュを照合してから時間・RSS・I/O回数をJSONへ保存します。既定では `build/benchmark.json` です。`--policy 0/1/2` で mmap・先読み・まとめ読みを比較できます。別の環境では記録済みベースラインとの倍率を同一条件の測定とは扱えません。

さらなる実装変更の前に比較用のエンジンを保存する場合:

```sh
make build/bench-model
cp build/bench-model /tmp/plamo-benchmark-reference
# 実装を変更して再ビルドした後
python3 tools/compare_engine.py --baseline /tmp/plamo-benchmark-reference
```

比較用のテンソルは `build/equivalence/` に置きます。基準テンソルを再利用する場合は `--reference-dumps build/equivalence/baseline` で、最適化後だけを実行できます。

単発CLI・`stream`の生成では大きな行列だけで約16.18 GBを毎ステップ読みます。約5秒の生成時間はこのI/Oの影響が大きく、CPUカーネルの倍率がそのまま全体の倍率にはなりません。ここに示す最適化は、精度と既存の手書きアセンブリ方式を維持した範囲のものです。

## 責務分離の前後比較（2026-11-11）

トークナイザー、Metalの重み管理とモデル実行、HTTPとワーカー通信、モデル記述子の生成、テストのビルド定義を整理しました。[構成と保つ条件](ARCHITECTURE.md)を参照してください。共通の抽象実行層へ統合する案と、既存の演算経路を維持して責務を分ける案を比較し、後者を採用しています。

Apple Silicon M2・24 GiBで、変更前の`dbed126`から保存したバイナリと変更後を交互に実行しました。各プロセスで2トークンのウォームアップ後に測定し、起動後・ウォームアップ後・測定後の保持量と形式が同じ組だけを比較しています。生成速度は入力処理を除く生成ステップ数／生成時間です。

| モデル・条件 | 比較組数 | 変更前 tokens/s | 変更後 tokens/s |
| --- | ---: | ---: | ---: |
| 0.8B・CPU 4スレッド・resident・32トークン | 5 | 22.256 | 22.319 |
| 0.8B・Metal・resident・32トークン | 5 | 49.440 | 49.600 |
| 2B・Metal・resident・32トークン | 3 | 14.859 | 14.909 |
| 8B・Metal・auto・候補検証あり・64トークン | 3 | 11.821 | 11.857 |

全16組で本文・生成ID・prefill後と生成後の全logits／状態ハッシュが一致しました。GPUコマンド数・dispatch数・明示的I/O量も同じです。8Bは両方とも実行用行列16,181,624,832バイトを12,295,471,104バイトに保持し、補助モデルの提案・採用数も一致しました。GPUの起動時割り当て量も各条件で同じです。生成速度の差は0.4%未満で、この小さな差を高速化の成果とは扱いません。

CLIのトークン化は、初期化を含む11組の中央値で34.355→34.296 msでした。英日・日英・長い入力・予約トークン・生プロンプトについて、固定接頭KVの有無を含む20組の出力と全ハッシュも変更前後で一致しました。

46本のネイティブテスト、54件のPythonテスト、4モデルのビルド・合成ローダー、モデルなしのソースからの`nix flake check`とインストール済みAPI起動コマンドのimportを確認しています。4モデルすべての生成アセンブリは変更前とバイト単位で一致し、演算カーネルのソースも同じです。

測定の生データ・バイナリとソースのSHA-256・保持量・起動時間・ピークRSSは[比較結果](benchmarks/refactor.json)に保存しています。OSのキャッシュや外部負荷は固定していません。8Bの`resident`は変更前バイナリが現在の空きメモリで全行列を保持しきれず、`auto`で比較しました。31Bの実生成・性能は測っていません。CPUの実測は0.8Bで、CPUカーネル自体は変更していません。
